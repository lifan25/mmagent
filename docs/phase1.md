# 第一阶段：复现准备与协作约定

2026-11-07 执行方式更新：用户已确认仓库建立并邀请成员；任务、结果和下一动作直接维护在 src/data_evaluation/TASKS.md、src/recommendation/TASKS.md、src/knowledge/TASKS.md。不要求 Issue、固定 PR 或首次协作合并。下文的报告和评审流程作为原始任务细目参考；实际完成判据采用材料齐备和同伴核对，不以创建任务单或合并请求作为验收条件。

## 目标和范围

第一阶段要回答：要复现什么、缺哪些材料、数据能否取得、用什么资源、三人如何衔接、下一阶段怎样验收。

本阶段不要求训练出论文指标，不以网站页面或模拟输出作为论文复现成果。

建议用一次启动会认领角色，再并行准备，最后做一次交叉评审。无教师期限，不把建议工作顺序当作已承诺的交付日期。

## 角色与交叉评审

| 角色 | 姓名 | 主要工作 | 交叉评审人 |
|---|---|---|---|
| A | 待填写 | 数据、实验协议、接口、仓库与集成准备 | B 检查数据/评估，C 检查知识接口 |

## A 的任务与交付

### A1：建立共同工作入口

- 创建 GitHub 仓库，邀请 B/C，填写角色姓名。
- 确认 main + 任务分支 + Pull Request 的协作方式。
- 创建本文件列出的任务，认领负责人；PR 指把分支修改提交给同伴评审的合并请求。
- 交付：仓库地址、任务入口、合并记录，填写 report-A.md。
- 完成：B/C 都能访问仓库；至少一位成员以任务分支提交过一次文档修改，并由另一位成员评审后合并。没有使用平台强制保护时，说明采用人工执行。

### A2：核实数据与计算资源

- MIMIC：每位实际接触受控数据的成员分别核实所需权限，不共享账号。记录“未申请 / 已提交 / 获批 / 已取得数据”等真实状态，不提交账号和证件。
- 诊断数据：由 C 检查 DXY/Muzhi 等下载入口，A 汇总版本、使用条件、可取得状态。
- 算力：先询问老师/学院是否能提供单卡资源，记录是否可用。未获资源时列明等待事项和负责人，不默认购买。
- 费用：大模型 API 与 GPU 是两类费用，分开列为“预算待确认”；没有试跑不编造总时长或总价。
- 交付：resources.md 的证据、申请状态、阻塞和下一动作。
- 完成：每项资源有来源、状态、负责人、下一动作；拿不到也应明确原因。申请已提交不等于可正式训练。

### A3：提出共同协议草案

- 与 B 确认诊断/操作/药物编码空间、历史记录、当前答案的边界。
- 与 C 确认来源、规则状态、未知信息和核查状态。
- 约定患者级划分、验证集选参、测试集使用和实验记录。
- 用 examples/ 的三个文件进行纸面走查，另外讨论“缺诊断”和“未知药物编码”两种情况。
- 交付：protocol.md 的评审修改和 report-A.md 的走查结论。
- 完成：B、C 逐项确认自己能提供或消费的字段；未确定项明确标注草案，不能写成已实现。

## B 的任务与交付

### B1：给出 SSPNet 复现说明

- 读清输入、输出、四个主要模块、训练目标和评价指标。
- 指明论文哪一节对应作者代码哪个文件/类。
- 先以 MIMIC-III 为首个运行目标；MIMIC-IV 保留在后续扩展清单，不声称已经完整复现。
- 列出运行入口、环境要求、需要的数据/映射/图文件，以及论文和代码的差异。
- 交付：report-B.md，附上游 URL、实际查看的 commit 或日期、方法到文件的对应表。
- 完成：A 能依照说明定位入口、知道输入文件如何取得、分清已核实和待索取项。

### B2：检查代码能启动到什么程度

- 在可用环境中检查依赖和入口；记录实际执行的命令、运行位置、结果和首个错误。
- 没有数据或 GPU 时，只检查可以真实执行的部分。下载成功、导入成功、完成训练分别记录。
- 不能为了显示“跑通”而编造输入文件、删除核心模块或用随机结果代替。
- 交付：report-B.md 中的启动检查记录与阻塞清单。敏感原始日志留在本地，只提交必要的已清理摘要。
- 完成：有实际检查证据或可核实的明确外部阻塞；未执行的项目写“未执行”。

### B3：列出首轮正式实验

- 完整 SSPNet、一个简单基线、去掉 PDRM 的关键对照。
- 列清数据、划分、参数、评价方式、种子、模型选取方式，待 A 确认。
- 交付：report-B.md 中的首轮运行计划，以及对 protocol.md 推荐接口的评审。
- 完成：数据与算力到位后，另一成员能按计划开始执行；无须本阶段产出训练指标。

## C 的任务与交付

### C1：给出 BIBM 原任务复现说明

- 区分知识检索、规则生成/迭代、Diaformer 问诊和 MLN 诊断。
- 选 DXY 或 Muzhi 作为首个数据集，检查实际下载可用性和使用条件。
- 查清 Diaformer 入口、MLN 工具、提示词、模型版本、生成规则等依赖。
- 第一篇完整作者实现尚未取得的部分列入索取清单，不自行补成论文事实。
- 交付：report-C.md 中的原论文复现计划、材料清单与来源。
- 完成：B 能根据说明分清各工具做什么，A 能看到数据和资源依赖。

### C2：准备知识核查协议与小样例

- 区分“原论文症状—疾病规则”与“未来扩展的用药规则”。
- 用规则模板整理至少 3 条用于讨论的规则记录：来源清楚的候选、信息不足无法判断的候选、无合适证据应退回的候选。可选公开资料；无法取得的内容如实记录。
- 三条记录均须标明审核状态，未审核规则不自动启用。若使用虚构逻辑样例，标明 synthetic，不附伪造医学来源。
- 交付：report-C.md 中的规则记录链接、边界示例，以及对 protocol.md 的知识核查接口评审。
- 完成：每条规则可追溯，知道需要哪些病例字段，能区分“无冲突”“信息不足”“根本没检查”；不要求证明这些规则已获临床有效性验证。

### C3：列出首轮正式实验与扩展边界

- 原 BIBM 流程与去掉规则迭代的对照，保持问诊证据条件一致。
- 用药核查先作为独立扩展，不把后处理效果写成 BIBM 原论文结论。
- 交付：report-C.md 的实验计划和待向老师索取的问题。
- 完成：原论文复现与新增扩展分别可验收。

## 并行顺序与依赖

1. 三人共同：认领角色、明确目标，提交第一轮任务。
2. A 建仓、申请资源；B 查 SSPNet；C 查 BIBM、诊断数据与知识来源，可同时推进。
3. B/C 报告自己的输入输出，A 汇总协议。
4. 三人用虚构样例走查，交叉评审各自报告。
5. A 汇总第一阶段验收与第二阶段就绪状态。

B/C 不必等待 MIMIC 审批才能读代码和整理依赖。正式训练依赖有效数据与计算条件。
