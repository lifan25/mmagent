# C：BIBM 诊断与知识核查模块

负责人：成员 C，账号待 A 指定。任务状态只更新 [TASKS.md](TASKS.md)。本模块包含原论文诊断分支和新增用药核查分支，分别记录与验收。

MLN 是马尔可夫逻辑网络，将逻辑规则与概率推理结合。用药核查分支先用明确规则检查候选，其来源与实现不能直接当作原 BIBM 的诊断结果。

## 先从这里开始

1. 阅读 [BIBM 原文](https://hdzhangust.github.io/static/files/papers/2023%20BIBM%20Integrating%20Automated%20Knowledge%20Extraction.pdf)、[现有 DXY 基线说明](../../docs/dxy-diaformer.md) 和 [资源缺口](../../docs/resources.md)。
2. 区分“检索得到的文字”“形式化的逻辑规则”“问诊已知事实”“推理输出”，写清每一步需要什么。
3. 看 [共享规则与核查协议](../../docs/protocol.md) 和 [规则模板](../../docs/templates/rule.md)，先整理来源与规则字段。
4. 先交 C1，不等待 B 的模型。C2 的诊断后端与 C3 的核查接口可分开推进；某一项受阻不必阻塞另一项。

## 建议实现文件，尚未创建

| 文件/目录 | 建议职责 |
|---|---|
| extract.py | 组织检索、摘要、规则生成/评分/迭代；记录所用模板与来源 |

规则模板以 docs/templates/rule.md 为准；共享状态以 docs/protocol.md 为准，不另创第二套规则字段或状态名。

## 两条分支的输入输出

| 分支 | 输入 | 输出和位置 |
|---|---|---|
| 原 BIBM 诊断 | DXY 已询问得到的症状、训练规则及学习设置 | .mln/.db、疾病推理结果、运行记录；留在 outputs/knowledge/ 等本地目录 |
| 用药核查扩展 | A 的 Case、B 的 Recommendation、已复核且编码相符的规则 | CheckReport：问题、来源、缺失事实、覆盖范围 |
| 离线接口检查 | 明确虚构病例、药物、规则 | synthetic_fixture 检查结果；不当作真实模型或医学证据 |

DXY 与住院病历没有患者对应关系，不做病例拼接。真实疾病标签、未询问隐藏症状不能进入诊断输入。

## 配置和检查建议

- configs/：本地后端路径、模型标识、检索来源、生成参数、迭代阈值、规则文件版本；密钥仅从环境读取，不写入配置或报告。
- prompts/：为每个模板附用途、输入占位、输出格式、原文出处和修改理由。不要只存一段无法追溯的聊天提示。
- rules/：候选先标 draft，组内复核后才能标 reviewed；与医学专家验证的含义分开。
- tests/：问题触发、执行后未发现冲突、缺条件信息、未加载/不适用规则；再覆盖否定、条件、未知药物与编码层级不一致。
- reports/：先交阶段流程与来源表，后续填真实后端命令、输入版本、运行结果及与原文的差异。病例和权重不提交。

## 技术建议

先做可追溯、范围小的流程。未配置大模型调用时，可整理模板和离线样例；Alchemy 环境受阻时，先推进独立核查接口，并把 C2 标为受阻。两者都不能替代真实后端运行或自动知识生成的验收。

用药核查先标记问题，保留 B 的原始候选，不擅自删除或补药；先证明规则执行正确，再讨论重排。若只增加标记，推荐准确率本身不会因此提高。

B 的真实编码未确定前，用共享虚构样例检查状态分支；确定后再选有来源、粒度合适的规则。3–5 条是首批目标，来源不够就少交，不按数量凑结论。
